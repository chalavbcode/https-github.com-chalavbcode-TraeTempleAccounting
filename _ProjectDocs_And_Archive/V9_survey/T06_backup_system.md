### g) Retention (FIFO) — tiers and new engine
- **Tiers** (DatabaseBackupHelper.vb:649-651 + Cleanup helpers l.815-853): Weekly ≤8, Monthly ≤15, Yearly ≤5; overwrite-in-place per ISO-week/month/year (same name → no new file); cleanup sorts by **file name** (OrdinalIgnoreCase, l.838) and deletes oldest beyond max, errors logged only. - **New engine**: **no retention at all** — sets are append-only; registry append-only (`AddEntry` never prunes, BackupRegistry.vb:117-121); scan is read-only; nothing deletes `Backup_2026*` sets. Receipts central folder explicitly append-only (l.733-741 comment + logic).
- **Can FIFO delete "the only complete one"?** Within its scope, the tier cleanup has **no safety interlock**: it never consults the registry/status and would delete the oldest week file purely by count (l.826-851). But tier files are **DB-only, never receipts-complete**, and live only in `AppRoot\Backup\{Weekly,Monthly,Yearly}`; complete sets (IsComplete=True) live on D:\ outside any retention path. So: retention cannot delete a "complete set" as the system defines them; it CAN delete an old DB-only tier snapshot without checking whether anything else is backed up (currently benign because 2 complete sets exist on D: — but the guard `SafetyCheckTwoDrives` (DatabaseBackupHelper.vb:430-435 → BackupStatusBuilder.BuildTwoDriveWarning l.744-760) is only *informational text*, not a gate on deletion).

## 5. Bonus finding — the DB rewrites itself every boot (explains "DB changed after backup")
`AccessDbProvider.SeedPositions` (AccessDbProvider.vb:232-260) runs on EVERY `EnsureSchema` (every app start): for each of 19 existing positions it executes `UPDATE Positions SET PositionGroup = @g WHERE PositionName = @n` (l.252-256) — an unconditional write, unlike SeedCategories/Funds/BankAccounts/Personnel which skip when data exists (count>0/name-exists guards). Evidence: DB file mtime = `2026-10-23 06:42` equals app boot `06:42:53` (RUNTIME: process StartTime 06:42:52 + crash.log line), and both complete registry entries carry problem `ฐานข้อมูลถูกแก้ไขหลังการสำรอง (hash ไม่ตรงกับปัจจุบัน)` even though no user edits occurred between backup and verification. Consequences: (i) every boot invalidates hash-match with all backups ("identical" can only hold within one run), (ii) increases OLEDB lock pressure at close-time backup, (iii) V8's "seeds only when empty" claim is CONTRADICTED for Positions.
