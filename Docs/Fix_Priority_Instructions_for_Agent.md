# คำสั่งสำหรับ AI Agent: แผนแก้ไขตามลำดับความเสี่ยง
**อ้างอิง:** System_Stability_and_Robustness_Audit.md (2026-08-09)
**เป้าหมาย:** ลดความเสี่ยงสูงสุดก่อน โดยแต่ละจุดที่แก้ต้อง "ปิดจบ" ในตัวเอง ไม่ทิ้งภาระทางเทคนิคใหม่ให้ต้องตามแก้ภายหลัง

---

## กติกาการทำงาน (บังคับทุกข้อ)

1. แก้ทีละจุดตามลำดับด้านล่าง **ห้ามข้ามลำดับ** และห้ามแก้หลายจุดพร้อมกันในคอมมิตเดียว
2. หลังแก้แต่ละจุด: `dotnet build -c Debug` และ `-c Release` ต้องได้ 0 warning / 0 error ก่อนไปจุดถัดไป
3. ห้ามแตะโค้ดส่วนที่ไม่เกี่ยวข้องกับจุดที่กำลังแก้ (no drive-by refactor) — ถ้าเจอปัญหาอื่นระหว่างทาง ให้บันทึกไว้เป็นรายการใหม่ ไม่ใช่แก้แทรก
4. ทุกจุดต้องมี "ขั้นตอนตรวจสอบ" ตามที่ระบุ รันจริงแล้วรายงานผลก่อนปิดงานจุดนั้น
5. เมื่อมีทางเลือกระหว่าง "แก้แบบเล็ก ปลอดภัย" กับ "แก้แบบใหญ่ ดีกว่าในระยะยาวแต่เสี่ยงกว่า" ให้เลือกแบบเล็กก่อนเสมอในรอบนี้ แล้วบันทึกแบบใหญ่ไว้เป็นงานแยกต่างหาก (ดูหมายเหตุจุดที่ 6)

---

## ลำดับการแก้ไข และเหตุผล

### จุดที่ 1 — DB-1: `EnsureSchema()` ล็อกสถานะผิดพลาดถาวร
**ไฟล์:** `Database.vb`
**ทำไมต้องแก้ก่อน:** เป็นจุดพื้นฐานที่สุดของทั้งระบบ — ถ้าไม่แก้ก่อน การทดสอบจุดอื่นๆ ทั้งหมดจะไม่น่าเชื่อถือ เพราะถ้า schema check ค้างในสถานะเสีย ทุกฟีเจอร์ที่ทดสอบทีหลังอาจ fail ด้วยสาเหตุนี้ ไม่ใช่จากบั๊กที่กำลังแก้จริง
**วิธีแก้:** ย้าย `_schemaChecked = True` ไปไว้ท้ายสุดของ `Try` (หลังทำงานสำเร็จทั้งหมดเท่านั้น) และ reset เป็น `False` ใน `Catch` ก่อน `Throw`
**เหตุผลที่ไม่ทิ้งปัญหาใหม่:** เป็นการสลับตำแหน่งบรรทัดล้วนๆ ไม่เปลี่ยน logic การสร้าง schema เลย ความเสี่ยง regression ต่ำมาก
**ตรวจสอบ:** จำลอง exception กลางทาง (เช่น comment migration step หนึ่งบรรทัดชั่วคราวให้ throw) แล้วยืนยันว่าเรียก `EnsureSchema()` ครั้งถัดไปยัง retry ได้จริง ไม่ค้างสถานะ `True`

### จุดที่ 2 — MM-1: `Directory.CreateDirectory` อยู่นอก Try/Catch
**ไฟล์:** `FrmExportForTransfer.vb`
**ทำไมอยู่อันดับสอง:** เป็นจุดเดี่ยว ไม่เกี่ยวพันกับโค้ดอื่น แก้ง่าย เสี่ยง regression ต่ำสุดในกลุ่ม HIGH ทั้งหมด เหมาะเก็บให้จบเร็วก่อนไปจุดที่ซับซ้อนกว่า
**วิธีแก้:** ย้ายบรรทัดเข้าไปอยู่ใน Try เดิมของ `btnExportForTransfer_Click`
**เหตุผลที่ไม่ทิ้งปัญหาใหม่:** ย้ายตำแหน่งบรรทัดเดียว ไม่เปลี่ยน flow การลบโฟลเดอร์เมื่อ error
**ตรวจสอบ:** export ไปยัง path ที่เขียนไม่ได้ (เช่น drive write-protected) ต้องเห็นข้อความ "ส่งออกไม่สำเร็จ" ตามที่ออกแบบไว้ ไม่ใช่ global crash dialog

### จุดที่ 3 — RP-2: ไม่มีการจำกัด `currentRowH` (infinite print loop)
**ไฟล์:** `IncomeExpenseReport.vb`
**ทำไมอยู่อันดับสาม:** แก้แบบเพิ่มการจำกัดค่า (cap) เพียงบรรทัดเดียว ไม่กระทบ layout ปกติเลยเพราะ cap จะทำงานเฉพาะกรณีสุดโต่งเท่านั้น
**วิธีแก้:** `currentRowH = Math.Min(currentRowH, maxRowH)` ตามที่ระบุในรายงาน
**เหตุผลที่ไม่ทิ้งปัญหาใหม่:** เป็น guard clause ที่ไม่ถูกใช้งานในกรณีปกติ (แถวสูงเกินหน้าเกิดยากมาก) จึงไม่กระทบรายงานที่พิมพ์ถูกต้องอยู่แล้ว
**ตรวจสอบ:** สร้างรายการทดสอบที่มีข้อความยาวผิดปกติ (~50,000 ตัวอักษร) แล้วสั่งพิมพ์ ต้องจบงานพิมพ์ได้ ไม่ค้าง

### จุดที่ 4 — RP-1: GDI+ leak ใน `IncomeExpenseReport` (ไม่มี Dispose)
**ไฟล์:** `IncomeExpenseReport.vb`, `BaseReport.vb`
**ทำไมอยู่อันดับสี่ ไม่ใช่อันดับแรก:** แม้ severity สูง แต่การเพิ่ม `Dispose` override มีความเสี่ยงเล็กน้อยที่ทำให้ font/pen ถูกปล่อยเร็วเกินไประหว่าง preview หลายหน้าในรอบพิมพ์เดียวกัน (lifecycle bug ใหม่) จึงควรแก้หลังจากฐานระบบ (จุด 1-3) มั่นคงแล้ว เพื่อแยกสาเหตุได้ง่ายถ้าเกิดปัญหาระหว่างทดสอบ
**วิธีแก้:** เพิ่ม `Protected Overrides Sub Dispose(disposing As Boolean)` เรียก `_theme.Dispose()` เฉพาะตอน object ทั้งใบถูกทิ้งจริง (ปิด preview/print เสร็จสมบูรณ์) — **ห้าม** เรียก dispose ระหว่างเปลี่ยนหน้า (page-to-page) ต้องตรวจ call site ให้แน่ใจว่า `Dispose()` ถูกเรียกครั้งเดียวตอนจบ lifecycle ของ report object เท่านั้น พร้อมลบหรือ dispose คลาส `BaseReport` ที่ตายแล้ว (dead code) ไปด้วย
**เหตุผลที่ไม่ทิ้งปัญหาใหม่:** ระบุชัดเจนว่าห้าม dispose ก่อนเวลา — ป้องกันไม่ให้เกิดบั๊กใหม่แบบ "พิมพ์หน้าที่ 2 แล้ว font หาย/ error"
**ตรวจสอบ:** พิมพ์ preview รายงานเดียวกัน 30 ครั้งติดกัน (ตามที่ audit ระบุ) เช็ค GDI handle count ด้วย Process Explorer ต้องคงที่ ไม่ไต่ขึ้นเรื่อยๆ และรายงานที่มีหลายหน้าในรอบเดียวต้องพิมพ์ครบถูกต้องทุกหน้า (ทดสอบ multi-page เพิ่มจากที่ audit แนะนำ เพื่อยืนยัน lifecycle ไม่พัง)

### จุดที่ 5 — MM-2 / MM-4: ไม่จำกัดขนาดไฟล์/จำนวนแถวก่อนอ่าน Excel
**ไฟล์:** `FrmMultiMachineImport.vb`
**ทำไมอยู่อันดับห้า:** เป็นจุดเดี่ยว ไม่เกี่ยวพันกับ transaction/threading แต่ต้องแก้ก่อนจุดที่ 6 เพราะจุดที่ 6 (UI-1) อยู่ใน flow เดียวกัน (multi-machine import) — ควรให้ input ปลอดภัยก่อนแล้วค่อยแก้เรื่อง concurrency ของ flow เดียวกัน จะทดสอบแยกสาเหตุได้ชัดกว่า
**วิธีแก้:** เช็ค `FileInfo.Length` เกิน 50 MB และจำกัดแถวใน `LoadWorksheet` ไม่เกิน 200,000 แถว ตามที่ระบุ พร้อม sanitize ชื่อ sheet ก่อนต่อ string เข้า `SELECT * FROM [...]`
**เหตุผลที่ไม่ทิ้งปัญหาใหม่:** ค่า limit ตั้งสูงพอที่จะไม่กระทบไฟล์งานจริงของวัด (ข้อมูลบัญชีวัดทั่วไปไม่ถึงหลักแสนแถว) จึงไม่กระทบผู้ใช้ปกติ
**ตรวจสอบ:** ทดสอบไฟล์ปกติ (import ได้เหมือนเดิม) และไฟล์เกิน 50MB/200k แถว (ต้องขึ้น SchemaError สุภาพ ไม่ OOM)

### จุดที่ 6 — UI-1: `Application.DoEvents()` ใน DB-transaction loop (re-entrancy)
**ไฟล์:** `FrmMultiMachineImport.vb`, `FrmLocationImport.vb`
**ทำไมอยู่อันดับสุดท้ายในกลุ่ม P0:** เป็นจุดที่มีความเสี่ยง regression สูงสุดในกลุ่มนี้ เพราะเกี่ยวกับ UI threading — ควรแก้หลังสุดเมื่อฐานระบบอื่นเสถียรแล้ว เพื่อให้ debug ง่ายหากมีผลข้างเคียง
**วิธีแก้ (เลือกแบบ minimal-safe ในรอบนี้ ไม่ใช่ full background-thread):**
- ลบ `Application.DoEvents()` ออกจาก loop
- ปิด (`Enabled = False`) ปุ่มทั้งหมดที่เกี่ยวข้อง (`btnSelectFiles`, `btnClearFiles`, `btnClose`, `btnViewDuplicates`) ตลอดช่วง `_isMerging = True`
- ใช้ `BeginInvoke` ที่มีอยู่แล้วสำหรับอัปเดต progress label แทนการพึ่ง `DoEvents()` ให้ UI repaint
**ทำไมไม่เลือกวิธี "ย้ายไป background thread" ในรอบนี้:** แม้เป็นทางแก้ที่ดีกว่าระยะยาว แต่เป็นการเปลี่ยนโครงสร้างใหญ่ (thread marshaling, exception handling ข้าม thread, การจัดการ transaction ข้าม thread) ซึ่งเปิดพื้นที่ให้เกิดบั๊กใหม่ประเภท concurrency ที่ตรวจจับยากกว่าของเดิม — ถ้าทำในรอบแก้ไขเร่งด่วนนี้โดยไม่มีรอบทดสอบเฉพาะของมันเอง มีโอกาสสูงที่จะสร้างปัญหาใหม่ให้ต้องตามแก้ภายหลัง จึงแนะนำให้บันทึกเป็น **งานแยกต่างหาก (P1.5 — background-thread migration)** พร้อมแผนทดสอบของตัวเอง ไม่ผูกกับรอบแก้ไข P0 นี้
**ตรวจสอบ:** ระหว่าง merge ไฟล์ขนาดใหญ่ ให้กดปุ่ม `btnClose`/`btnSelectFiles` รัวๆ ต้องไม่มีผลใดๆ จนกว่า merge จะเสร็จ และไม่มี transaction ซ้อนเกิดขึ้น (เช็คจาก log)
