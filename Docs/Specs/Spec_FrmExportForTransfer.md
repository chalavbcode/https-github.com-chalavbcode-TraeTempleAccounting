# Spec เพิ่มเติม: FrmExportForTransfer.vb — ส่งออกข้อมูลเพื่อนำไปนำเข้าเครื่องอื่น

เอกสารนี้เป็นส่วนเสริมของ `Spec_FrmMultiMachineImport.md` — จุดประสงค์คือทำให้ **ฝั่งส่งออก (Export)** และ **ฝั่งนำเข้า (Import)** ใช้โครงสร้างข้อมูลชุดเดียวกัน เพื่อให้ dedup และ MachineID tracking ที่ออกแบบไว้ในฝั่ง import ทำงานได้จริง ไม่ใช่แค่ทำงานได้ในทางทฤษฎี

---

## 0. หลักการสำคัญที่สุด: GUID ต้องเกิดตอน "บันทึกรายการ" ไม่ใช่ตอน "ส่งออก"

**นี่คือการเปลี่ยนแปลงที่กระทบไฟล์นอกเหนือจากฟอร์ม export/import** — ต้องแก้ที่จุดบันทึกธุรกรรมหลักของระบบ (ฟอร์ม/ฟังก์ชันที่ใช้บันทึกรายรับ-รายจ่ายปกติ) ไม่ใช่แค่สร้างฟอร์มใหม่

- เพิ่มคอลัมน์ `TransactionGUID` (Text/GUID, nullable) ในตารางธุรกรรมหลัก ถ้ายังไม่มี
- แก้จุดบันทึกรายการเดิม ให้ generate `Guid.NewGuid()` ทันทีตอน insert รายการใหม่ทุกครั้ง
- รายการเก่าที่มีอยู่แล้วในฐานข้อมูล (ก่อนมีคอลัมน์นี้) จะไม่มี GUID — ให้ export/import fallback ไปใช้ composite key ตามที่ระบุในสเปค import (ข้อ 4) สำหรับรายการเก่าเท่านั้น
- **ข้อควรระวัง:** การแก้จุดนี้เสี่ยงกระทบการทำงานเดิมของระบบมากที่สุดในทั้งโปรเจกต์ ควรให้ AI agent แสดง diff ของไฟล์ที่แก้ให้ตรวจสอบก่อน commit และทดสอบการบันทึกรายการปกติซ้ำหลายครั้งหลังแก้ ว่ายังทำงานถูกต้องเหมือนเดิมทุกกรณี (ไม่ error ถ้า field GUID เป็น null สำหรับ query เก่าที่ยังไม่ได้อัปเดต)

---

## 1. Machine ID: ต้องตั้งค่าครั้งเดียวต่อเครื่อง ไม่ใช่สุ่มทุกครั้งที่ export

- เพิ่มตาราง/ไฟล์ config ในเครื่อง (เช่น ตาราง `LocalSettings` ในฐานข้อมูล หรือไฟล์ config แยกในเครื่องนั้น) เก็บค่า `MachineID` ที่ผู้ดูแลตั้งครั้งเดียวตอนติดตั้งโปรแกรม (เช่น "KIOSK-01", "สำนักงานหลัก")
- ถ้ายังไม่เคยตั้งค่า ให้ระบบแจ้งเตือนตอนกดปุ่ม export ครั้งแรกให้ตั้งชื่อเครื่องก่อน ไม่ export ทันทีโดยไม่มี MachineID
- `MachineID` นี้คือค่าเดียวกับที่ฝั่ง import จะอ่านมาแสดงในคอลัมน์ preview ตามสเปคเดิม

## 2. FrmExportForTransfer.vb — ฟอร์มส่งออก

### รูปแบบการเปิดฟอร์ม
เช่นเดียวกับ `FrmMultiMachineImport.vb` ฟอร์มนี้ต้องเปิดแบบ **Modal Dialog (`.ShowDialog()`)** ไม่ใช่ฝังใน `pnlFormHostBody` ผ่าน `ShowFormInPanel(...)` เหตุผลเดียวกัน: การ export มีขั้นตอน copy ไฟล์แนบซึ่งใช้เวลา ถ้าฝังใน panel แล้วผู้ใช้สลับเมนูระหว่างทำงาน ฟอร์มจะถูก `CloseActiveForm(): Dispose` กลางคัน เสี่ยงไฟล์ export ไม่สมบูรณ์

### ปุ่มหลัก
- `btnExportForTransfer` ("ส่งออกข้อมูลไปเครื่องอื่น")

### ตัวเลือกช่วงข้อมูลที่ส่งออก
- **ส่งออกเฉพาะรายการใหม่ตั้งแต่ครั้งล่าสุด** (ค่าเริ่มต้น/แนะนำ) — อิงจาก `ExportHistory` ของเครื่องนั้น
- **ส่งออกตามช่วงวันที่ที่เลือกเอง** — สำหรับกรณีต้องส่งซ้ำหรือย้อนหลัง
- **ส่งออกทั้งหมด** — ใช้เฉพาะกรณีจำเป็น เช่น ตั้งเครื่องใหม่

### โครงสร้างไฟล์ export ที่ต้องมี (ให้ import อ่านได้ตรงกัน)
ไฟล์ export ต้องมี **header/metadata block** แยกจากข้อมูลตาราง เพื่อให้ฝั่ง import ตรวจสอบได้ก่อนเปิดอ่านข้อมูลจริง:

| ข้อมูลใน Header | คำอธิบาย |
|---|---|
| `MachineID` | รหัสเครื่องต้นทาง (ข้อ 1) |
| `ExportDateTime` | วันเวลาที่ export |
| `SchemaVersion` | เลขเวอร์ชันโครงสร้างไฟล์ (ดูข้อ 3) |
| `RowCount` | จำนวนแถวในไฟล์ (ให้ import เช็คว่าตรงกับที่อ่านได้จริงหรือไม่ กันไฟล์เสีย/ถูกตัดกลางทาง) |

ข้อมูลรายแถวต้องมีอย่างน้อย: `TransactionGUID` (อาจว่างสำหรับรายการเก่า), `TranDate`, `Amount`, `Type`, `Description` — ชื่อคอลัมน์และลำดับต้องตรงกับที่ `FrmMultiMachineImport.vb` คาดหวังไว้เป๊ะ

### ExportHistory (ตารางคู่กับ ImportHistory)
เก็บ log ทุกครั้งที่กด export สำเร็จ: `ExportBatchID, ExportDateTime, DateRangeFrom, DateRangeTo, RowCount, FileNameGenerated`
ใช้เพื่อให้ปุ่ม "ส่งออกเฉพาะรายการใหม่" รู้ว่าจะเริ่มจากจุดไหน และป้องกันความสับสนว่า export อะไรไปแล้วบ้าง

## 3. Schema Version — กันปัญหาเครื่องอัปเดตโปรแกรมไม่พร้อมกัน

ในความเป็นจริง เครื่องแต่ละเครื่องอาจอัปเดตโปรแกรมคนละเวลากัน ทำให้โครงสร้างไฟล์ export เปลี่ยนไปคนละเวอร์ชัน

- กำหนดค่าคงที่ `SCHEMA_VERSION` ในโค้ด (เช่น "1.0") ฝังลงใน header ตอน export
- ฝั่ง `FrmMultiMachineImport.vb` ต้องเช็คค่านี้ก่อนอ่านข้อมูล ถ้าเวอร์ชันไม่ตรงกับที่ฟอร์ม import รองรับ ให้แจ้งเตือนชัดเจน ("ไฟล์นี้มาจากโปรแกรมเวอร์ชันที่ต่างกัน อาจอ่านข้อมูลผิดพลาด") แทนที่จะพยายามอ่านแล้ว error แบบไม่ทราบสาเหตุ

---

## ข้อควรระวัง (เพิ่มเติมเฉพาะฝั่ง export — ไม่ซ้ำกับฝั่ง import)

1. **ไม่ต้องทำ auto-export อัตโนมัติตามตารางเวลา** — ให้เป็นการกดปุ่มด้วยมือเท่านั้น เพื่อให้ผู้ดูแลควบคุมได้ว่าเอาไฟล์ไปไว้ที่ไหน/ใส่ Flash Drive อันไหน ลดความเสี่ยงข้อมูลหลุดออกไปโดยไม่ตั้งใจ
2. **ห้ามให้ export แก้ไขข้อมูลต้นฉบับ** — เป็นการอ่านอย่างเดียว (read-only query) ห้าม mark สถานะใดๆ ในตารางธุรกรรมต้นฉบับว่า "ถูก export แล้ว" เพราะจะกระทบ logic เดิมของระบบบันทึกบัญชี ให้ใช้ `ExportHistory` แยกต่างหากในการติดตามแทน
3. **ตั้งชื่อไฟล์ export ให้มี MachineID + วันที่ฝังอยู่ในชื่อไฟล์ด้วย** (เช่น `Export_KIOSK-01_20260808.xlsx`) เพื่อความสะดวกของผู้ใช้งานตอนเลือกไฟล์ แต่ย้ำว่า**ระบบต้องไม่พึ่งพาชื่อไฟล์เป็นแหล่งความจริง** ยึด MachineID ที่ฝังใน header เป็นหลักเสมอ ชื่อไฟล์เป็นแค่ความสะดวกสายตา
4. **ทดสอบ round-trip ก่อนใช้งานจริง** — export จากเครื่อง A แล้วลอง import เข้าเครื่อง B (หรือฐานข้อมูลทดสอบ) ดูว่าจำนวนแถว/ยอดเงินตรงกันทั้งหมด ก่อนนำไปใช้กับข้อมูลจริงของวัด

## Deliverables เพิ่มเติมจาก AI Agent

1. ไฟล์ `FrmExportForTransfer.vb` (+ `.Designer.vb`) ใหม่
2. Script สร้างตาราง `ExportHistory`, `LocalSettings` (ถ้ายังไม่มี) และคอลัมน์ `TransactionGUID` ในตารางธุรกรรมหลัก
3. **แก้ไขจุดบันทึกธุรกรรมเดิม** (ระบุชื่อไฟล์ที่แก้ให้ชัดเจนในรายงานผล) เพื่อ generate GUID ตอนบันทึกรายการใหม่ — พร้อมสรุปว่าทดสอบการบันทึกปกติแล้วไม่กระทบพฤติกรรมเดิม
4. เพิ่มปุ่ม `"ส่งออกข้อมูลไปเครื่องอื่น"` ใน `pnlSidebar` ของ `frmMain.vb` (จุดเดียวกับที่เพิ่มปุ่ม import) — event handler เรียก `New FrmExportForTransfer().ShowDialog()` โดยตรง ไม่ผ่าน `ShowFormInPanel(...)`
5. รายงานผลการทดสอบ round-trip (export → import) อย่างน้อย 1 รอบ พร้อมตัวเลขจำนวนแถว/ยอดเงินที่ตรงกัน
