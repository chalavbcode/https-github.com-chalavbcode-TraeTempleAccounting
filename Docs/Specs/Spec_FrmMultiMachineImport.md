# Spec: FrmMultiMachineImport.vb — นำเข้าและรวมข้อมูลจากหลายเครื่อง/หลาย Flash Drive

## บทบาทและเป้าหมาย

สร้างฟอร์มใหม่ชื่อ `FrmMultiMachineImport.vb` สำหรับนำเข้า ตรวจสอบ และรวม (merge) ข้อมูลธุรกรรมออฟไลน์จากหลายเครื่อง/หลาย Flash Drive เข้าสู่ฐานข้อมูลหลัก (`TempleAccounting.accdb`)

**ห้ามแก้ไข `ExcelTransactionImport.vb` ที่มีอยู่เดิมโดยเด็ดขาด** — ให้สร้างฟอร์มใหม่แยกต่างหาก และใช้ฟังก์ชัน/คลาสร่วม (shared helper) แบบ read-only reference เท่านั้นถ้าจำเป็นต้องเรียกใช้โค้ดเดิม

### สถาปัตยกรรมที่ยืนยันแล้วจากโปรเจกต์เดิม (ต้องทำตามให้ตรง)

โปรเจกต์นี้ใช้ single-process WinForms, `frmMain` เป็น shell กลาง มีฟอร์มลูก 2 รูปแบบ:
- **ฝังใน Panel** (`pnlFormHostBody`) ผ่าน `ShowFormInPanel(childForm, title)`: `TopLevel=False, Border=None, Dock=Fill` — ใช้กับฟอร์มหลักที่อยู่ในเมนูหลัก เช่น `FrmIncome, FrmExpense, FrmTransactions, FrmReports`. ฟอร์มกลุ่มนี้จะถูก **`CloseActiveForm(): Remove+Close+Dispose`** ทันทีที่ผู้ใช้กดเมนูอื่นเพื่อสลับหน้า
- **Modal Dialog** ผ่าน `.ShowDialog()` — ใช้กับฟอร์มงานบริหารจัดการ/เสริม เช่น `FrmPersonnelManagement, FrmHelpDialog`

**`FrmMultiMachineImport.vb` ต้องเปิดแบบ Modal Dialog (`.ShowDialog()`) ไม่ใช่ฝังใน Panel** เหตุผล: กระบวนการ merge ใช้ OLEDB Transaction + การ copy ไฟล์แนบแบบ staging (ดูสเปคไฟล์แนบ) ซึ่งใช้เวลาและต้องทำให้เสร็จสมบูรณ์แบบ all-or-nothing ถ้าฟอร์มฝังอยู่ใน panel แล้วผู้ใช้เผลอกดเมนูอื่นระหว่าง merge กำลังทำงาน ฟอร์มจะถูก `Dispose` กลางคันโดย `CloseActiveForm()` เสี่ยงทำให้ transaction ค้างหรือ commit ไปครึ่งเดียว การเปิดแบบ Modal จะบล็อกไม่ให้แตะ sidebar ได้จนกว่าฟอร์มจะปิดเอง ตัดความเสี่ยงนี้ทิ้งไปทั้งหมดโดยไม่ต้องเขียน logic ป้องกันเพิ่ม

Shared module ที่มีอยู่แล้วในโปรเจกต์และควรเรียกใช้ซ้ำแทนการเขียนใหม่: `Db`, `AppPaths`, `ReceiptImageHelper`, `DatabaseBackupHelper` (ใช้สำหรับข้อกำหนด backup ก่อน merge ในข้อ 5), `ExcelTransactionImporter`

## 2. Machine Identification & File Hash Tracking (ส่วนสำคัญที่ต้องเพิ่ม)

เป้าหมายของส่วนนี้คือทำให้ระบบ **"รู้จริง"** ว่าข้อมูลแต่ละแถวมาจากเครื่องไหน และ **กันการนำเข้าไฟล์ซ้ำ** แม้จะถูกเปลี่ยนชื่อไฟล์แล้วก็ตาม

### 2.1 Machine ID ที่ฝังมาในไฟล์ export (ไม่ใช่ชื่อไฟล์)

- ไฟล์ export จากเครื่องปลายทางต้องมี field `MachineID` หรือ `KioskCode` ฝังอยู่ในตัวไฟล์เอง (เช่น ในแถว header หรือ hidden sheet/cell คงที่) — **ห้ามใช้ชื่อไฟล์หรือ Windows PC Name เป็นตัวระบุเครื่อง** เพราะเปลี่ยนแปลง/เผลอแก้ได้ง่าย
- ถ้าไฟล์ export เดิมยังไม่มี field นี้ ให้ระบบแจ้งเตือนชัดเจนว่า "ไม่พบรหัสเครื่องต้นทางในไฟล์นี้ ระบบจะใช้ชื่อไฟล์แทน (ความน่าเชื่อถือต่ำ)" — ไม่ควร block การทำงาน แต่ต้องให้ผู้ใช้เห็นระดับความเชื่อถือได้ของแหล่งที่มา
- แสดง `MachineID` ที่อ่านได้จริงจากไฟล์ในคอลัมน์ preview แยกจากชื่อไฟล์ที่ผู้ใช้ตั้ง

### 2.2 File Hash (SHA-256) เพื่อกันไฟล์ซ้ำ

- ก่อนเปิดอ่านข้อมูลในไฟล์ ให้คำนวณ SHA-256 hash ของไฟล์ทั้งไฟล์ทันที
- เช็ค hash นี้กับตาราง `ImportHistory` ในฐานข้อมูลหลัก
  - ถ้า hash ตรงกับที่เคย import สำเร็จไปแล้ว → **แจ้งเตือนทันทีก่อนแม้แต่จะแสดง preview** ว่า "ไฟล์นี้เคยถูกนำเข้าระบบแล้วเมื่อ [วันที่] โดย [ผู้ใช้]" พร้อมปุ่มยืนยันว่าจะ "นำเข้าซ้ำแบบตั้งใจ" หรือ "ข้ามไฟล์นี้"
  - ห้าม auto-skip แบบเงียบๆ — ต้องให้ผู้ใช้ตัดสินใจเอง เพราะบางกรณีอาจตั้งใจ re-import จริง (เช่น import ครั้งก่อน rollback ไปแล้ว)

### 2.3 ตาราง ImportHistory (ต้องสร้างใหม่ในฐานข้อมูล)

สร้างตารางใหม่ (ไม่กระทบตารางเดิม) เก็บ:

| Field | คำอธิบาย |
|---|---|
| `ImportBatchID` (GUID, PK) | รหัสการนำเข้าแต่ละครั้ง |
| `SourceFileName` | ชื่อไฟล์ตอนเลือก (เพื่ออ้างอิง ไม่ใช่ตัวระบุหลัก) |
| `FileHash` | SHA-256 ของไฟล์ |
| `MachineID` | รหัสเครื่องต้นทางที่อ่านได้จากไฟล์ (ถ้ามี) |
| `ImportDateTime` | วันเวลาที่ merge สำเร็จ |
| `ImportedBy` | ผู้ใช้ที่ทำรายการ (ถ้าระบบมี login) |
| `RowCountTotal` | จำนวนแถวทั้งหมดในไฟล์ |
| `RowCountImported` | จำนวนแถวที่ merge เข้าจริง |
| `RowCountSkippedDuplicate` | จำนวนแถวที่ข้ามเพราะซ้ำ |
| `TotalAmountImported` | ยอดรวมเงินที่นำเข้าจริง |

### 2.4 การเก็บที่มาลงในตารางธุรกรรมจริง (ไม่ใช่แค่โชว์ใน preview)

- ทุกแถวที่ merge เข้าตารางธุรกรรมหลัก ต้องมีการอ้างอิงกลับไปที่ `ImportBatchID` (foreign key) เพื่อให้สามารถสืบย้อนได้ในอนาคตว่าแถวไหนมาจากการ import ครั้งไหน/เครื่องไหน
- ถ้าตารางธุรกรรมหลักยังไม่มีคอลัมน์นี้ ให้เพิ่มคอลัมน์ `ImportBatchID` (nullable, ค่า default เป็น NULL สำหรับข้อมูลเดิมที่บันทึกในระบบโดยตรงอยู่แล้ว) — เป็นการเพิ่มแบบ non-breaking ไม่กระทบข้อมูลเดิม

## 3. Data Preview Grid (`dgvImportPreview`)

แสดงสรุปต่อไฟล์ก่อน merge จริง คอลัมน์:

- `Source File Name` (ชื่อไฟล์)
- `Machine ID` (จากข้อ 2.1 — ถ้าอ่านไม่ได้ให้โชว์ "ไม่ทราบ/Unknown")
- `File Hash Status` ("ใหม่" / "เคย Import แล้วเมื่อ...")
- `Total Transactions Count`
- `Total Income Sum`
- `Total Expense Sum`
- `Duplicate Status` ("Ready" / "พบรายการซ้ำ N รายการ")

**เพิ่มเติมจากสเปคเดิม:** ต้องมีปุ่มหรือ double-click เพื่อ "ดูรายการที่ตรวจพบว่าซ้ำ" แบบละเอียดก่อนตัดสินใจ ห้าม auto-skip โดยผู้ใช้ไม่เห็นเลยว่าอะไรถูกข้ามไปบ้าง เพราะ composite key อาจตรวจผิดพลาด (false positive) ได้ในกรณีที่มีธุรกรรมยอดเงิน/วันที่/ประเภทตรงกันโดยบังเอิญ

## 4. Smart Deduplication Logic

ตรวจสอบซ้ำโดยเรียงลำดับความสำคัญดังนี้:

1. **`TransactionGUID`** (ถ้ามีในข้อมูลต้นทาง) — วิธีที่แม่นยำที่สุด เพราะไม่ขึ้นกับเนื้อหาข้อมูล
2. ถ้าไม่มี GUID ให้ fallback ไปที่ composite key `(TranDate + Amount + Type + Description + MachineID)` — **เพิ่ม `MachineID` เข้าไปในคีย์ด้วย** เพื่อลดโอกาสชนกันข้ามเครื่อง เทียบกับสเปคเดิมที่ไม่มี MachineID ในคีย์เลย
3. ถ้า fallback composite key ตรวจพบว่าซ้ำ ให้ถือเป็น "น่าสงสัย" (suspected duplicate) ไม่ใช่ "ซ้ำแน่นอน" — แสดงในกลุ่มแยกให้ผู้ใช้ยืนยันเอง แทนที่จะข้ามอัตโนมัติทันที

ตรวจกับฐานข้อมูลหลักทุกครั้ง (ไม่ใช่ตรวจแค่ภายในไฟล์ที่เลือกพร้อมกัน)

## 5. Merge Execution & Transaction Handling

- ปุ่ม `btnConfirmMerge` ("บันทึกรวมข้อมูลลงฐานข้อมูลหลัก")
- **ก่อน merge ทุกครั้ง ให้สำรอง (backup) ไฟล์ `TempleAccounting.accdb` อัตโนมัติ** เป็นไฟล์แยก (เช่น ใส่วันที่-เวลาในชื่อไฟล์) เก็บไว้ในโฟลเดอร์ backup — เหตุผล: OLEDB Transaction ป้องกัน insert ผิดพลาดระหว่าง merge ได้ แต่ไม่ได้ป้องกันไฟล์ .accdb เสียหาย/corrupt ระหว่างกระบวนการ ซึ่งเกิดขึ้นได้กับไฟล์ Access โดยเฉพาะถ้าไฟล์มีขนาดใหญ่หรือถูกเปิดค้างจากเครื่องอื่น
- ครอบการ insert ทั้งหมดด้วย OLEDB Transaction block — commit ต่อเมื่อทุกแถวสำเร็จ, rollback ทั้งหมดถ้ามี error แม้แต่แถวเดียว
- บันทึกผลลัพธ์ลงตาราง `ImportHistory` เฉพาะเมื่อ commit สำเร็จเท่านั้น
- แสดงข้อความสรุปหลัง merge สำเร็จ: จำนวนแถวที่นำเข้า, จำนวนที่ข้าม (ซ้ำ), ยอดเงินรวมที่เพิ่มเข้าไป, และ Machine ID ของแต่ละไฟล์ที่นำเข้า

## ข้อควรระวังเพิ่มเติม (สำคัญแต่ไม่เพิ่มความซับซ้อนเกินจำเป็น)

ข้อควรระวังด้านล่างนี้เลือกมาเฉพาะจุดที่มีความเสี่ยงจริงต่อความถูกต้องของข้อมูลบัญชี ไม่ใช่ทุกอย่างที่เป็นไปได้ — ตั้งใจไม่เพิ่มฟีเจอร์ที่ซับซ้อนเกินความจำเป็น (เช่น ไม่ต้องทำระบบ multi-user locking แบบเต็มรูปแบบ หรือ real-time sync ข้ามเครื่อง เพราะงานนี้เป็นการ import แบบ batch เป็นครั้งคราว ไม่ใช่ระบบ concurrent)

1. **Validate schema ของไฟล์ก่อนอ่านข้อมูลจริง** — เช็คว่าคอลัมน์ที่จำเป็น (TranDate, Amount, Type, Description) มีอยู่ครบก่อน ถ้าไฟล์ผิดรูปแบบให้แจ้งเตือนและข้ามไฟล์นั้น ไม่ทำให้ทั้งโปรแกรม crash
2. **ตรวจสอบความสมเหตุสมผลของวันที่ (Sanity check TranDate)** — ถ้าพบ TranDate ในอนาคต หรือย้อนหลังเกินกว่าที่เป็นไปได้ (เช่น นาฬิกาเครื่องต้นทางเพี้ยน) ให้ flag เตือนในหน้า preview ไม่ต้อง block แต่ให้ผู้ใช้เห็นความผิดปกติก่อนตัดสินใจ merge
3. **ห้าม auto-skip รายการที่ตรวจพบว่าซ้ำแบบเงียบๆ** — ต้องให้ผู้ใช้เห็นและยืนยันเสมอ ตามที่ระบุในข้อ 3-4
4. **Backup ฐานข้อมูลก่อน merge ทุกครั้ง** ตามข้อ 5 — เป็นเซฟตี้เน็ตสุดท้ายถ้าเกิดปัญหาที่ transaction rollback ช่วยไม่ได้
5. **ปิด/ล็อกการกดปุ่ม `btnConfirmMerge` ซ้ำระหว่างกำลัง merge อยู่** (disable ปุ่มระหว่างประมวลผล) เพื่อกันผู้ใช้กดซ้ำจนเกิด transaction ซ้อนกัน
6. **Log ผลลัพธ์การ merge ทุกครั้งลง `ImportHistory`** แม้กรณีที่ผู้ใช้ยกเลิกหรือเกิด error กลางทาง (บันทึกสถานะ "Failed"/"Cancelled" ไว้ด้วย) เพื่อให้ตรวจสอบย้อนหลังได้ครบ ไม่ใช่แค่ log เฉพาะตอนสำเร็จ
7. **ไม่ต้อง implement การ auto-sync หรือ auto-detect USB drive แบบ real-time** — ให้ผู้ใช้เลือกไฟล์เองผ่าน dialog ตามสเปคเดิม เพื่อลดความซับซ้อนและความเสี่ยงจากการ trigger import โดยไม่ตั้งใจ
