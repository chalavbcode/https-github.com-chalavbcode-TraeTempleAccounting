# Spec เพิ่มเติม: การจัดการไฟล์แนบใบเสร็จ/สลิป (Receipt Attachments) ในระบบ Export/Import หลายเครื่อง

เอกสารนี้เป็นส่วนเสริมของ `Spec_FrmMultiMachineImport.md` และ `Spec_FrmExportForTransfer.md` เนื่องจากระบบบันทึกบัญชีของวัดมีการแนบไฟล์รูปใบเสร็จ/สลิปต่อรายการอยู่แล้ว จึงต้องออกแบบให้ export/import พาไฟล์แนบเหล่านี้ไปด้วยอย่างถูกต้อง ไม่ใช่ย้ายแค่ตัวเลข

---

## 0. ข้อมูลที่ยืนยันแล้ว + สิ่งที่ AI Agent ยังต้องไปหาต่อ

### ยืนยันแล้วจากโค้ดจริงและเอกสารสถาปัตยกรรมโปรเจกต์ (`PROJECT_PROFILE_V4.md`) — ไม่ต้องให้ agent เดาหรือตรวจสอบใหม่

- **ระบบเก็บไฟล์แนบเป็นแบบที่ 1 — path อ้างอิงไปยังไฟล์แยกในโฟลเดอร์** ยืนยันจาก:
  - คอลัมน์ `Transactions.ReceiptPath` เก็บ**ชื่อไฟล์** (ไม่ใช่ path เต็ม ไม่ใช่ BLOB) ผ่านคำสั่ง `UPDATE Transactions SET ReceiptPath=@p WHERE ID=@id`
  - ตัวอย่างชื่อไฟล์จริงที่เห็น: `Receipt_12`, `Receipt_13`, `Receipt_56` ... — สร้างจาก **`ID` ของตาราง `Transactions` เอง (auto-increment)** ไม่ใช่ GUID → นี่คือจุดเสี่ยงชื่อไฟล์ชนกันเวลารวมหลายเครื่อง ตามที่ระบุไว้แล้วในสเปคนี้ (ต้อง rename เป็น `{TransactionGUID}.xxx` ตอน export)
  - ฟังก์ชันที่ใช้บันทึกไฟล์คือ `ReceiptImageHelper.SaveOptimizedReceipt(image, id)` — ชื่อฟังก์ชันระบุชัดว่า**มีการ optimize/บีบอัดรูปตอนบันทึกแล้ว** → export/import ต้อง copy ไฟล์ที่ optimize แล้วไปตรงๆ **ห้าม re-process ซ้ำ** ไม่งั้นคุณภาพรูปเสียซ้ำสอง
  - `ReceiptImageHelper` เป็น **shared module ที่มีอยู่แล้วในโปรเจกต์** (ยืนยันจากรายการ shared modules ใน `PROJECT_PROFILE_V4.md`) — agent ควรเรียกใช้ฟังก์ชันที่มีอยู่ (เช่นฟังก์ชันหาตำแหน่งไฟล์จริงจากชื่อ) แทนการเขียน logic หาตำแหน่งไฟล์ขึ้นใหม่เอง
  - การแนบรูปเป็นการ **UPDATE แยกทีหลัง** ไม่ใช่ตอน insert รายการครั้งแรก → คอลัมน์ `ReceiptPath` **อาจเป็นค่าว่างได้** export ต้องเช็คค่าว่างก่อนเสมอ ไม่ใช่ทุกแถวมีไฟล์แนบ

- **พบปัญหา duplicate event handler ในฟอร์มบันทึกรายการหลัก** ที่ต้องระวังเป็นพิเศษก่อนแก้ไฟล์นี้:
  ```vb
  Private Sub btnPasteReceipt_Click(...) Handles btnPasteReceipt.Click   ' ตัวจริง มีโค้ดทำงาน
  Private Sub btnPasteReceipt_Click_1(...) Handles btnPasteReceipt.Click ' ตัวว่างเปล่า ค้างจาก Designer
  ```
  ทั้งสอง Sub ผูกกับปุ่มเดียวกันและทำงานพร้อมกันทั้งคู่โดยไม่ error ตอน compile — **ก่อนแก้ไฟล์นี้ ให้ agent ลบ `_Click_1` (ตัวว่าง) ทิ้งก่อน แล้วแก้เฉพาะ `_Click` (ตัวจริง) เท่านั้น** และให้ตรวจทั้งไฟล์ว่ามี pattern แบบนี้ที่จุดอื่นอีกหรือไม่ ก่อนเริ่มแก้งานตามสเปค เพราะถ้า agent เผลอไปแก้ตัวว่าง งานทั้งหมดจะไม่มีผลอะไรเลยโดยไม่มี error ให้สังเกต

### สิ่งที่ agent ยังต้องไปหาเพิ่มเอง (2 อย่างที่เหลือ)

1. **path จริงของโฟลเดอร์เก็บไฟล์แนบ** — เปิดดูคลาส `AppPaths` (โดยเฉพาะ `AppPaths.EnsureDirectoriesExist()` และ property/constant ที่เกี่ยวกับ Receipt) เพื่อหาตำแหน่งโฟลเดอร์จริงบนเครื่อง
2. **นามสกุลไฟล์ที่บันทึกจริง** (.jpg/.png) — เปิดดูภายใน `ReceiptImageHelper.SaveOptimizedReceipt` เพื่อยืนยัน

ให้ agent รายงานผล 2 ข้อนี้กลับมาก่อน แล้วค่อยดำเนินการตามหัวข้อด้านล่าง

## 1. ฝั่ง Export — พาไฟล์แนบไปด้วย

- เวลา export รายการธุรกรรม ให้ export ไฟล์แนบที่ผูกกับรายการนั้นไปด้วย โดยเก็บไว้ใน **โฟลเดอร์ย่อย** ควบคู่กับไฟล์ข้อมูล เช่น
  ```
  Export_KIOSK-01_20260808/
    ├── TransactionData.xlsx
    └── Receipts/
         ├── {TransactionGUID}.jpg
         ├── {TransactionGUID}.jpg
         └── ...
  ```
- **ตั้งชื่อไฟล์แนบด้วย `TransactionGUID` ไม่ใช่ชื่อไฟล์เดิม** เพื่อป้องกันชื่อไฟล์ชนกันเมื่อรวมไฟล์จากหลายเครื่อง (เช่น ทุกเครื่องอาจมีไฟล์ชื่อ "IMG_001.jpg" ซ้ำกันได้)
- **รายการที่ไม่มี `TransactionGUID`** (รายการเก่าก่อนมีการเพิ่ม GUID ตามสเปคก่อนหน้า) → ไม่สามารถจับคู่ไฟล์แนบได้อย่างปลอดภัยอัตโนมัติ ให้ข้ามการ export ไฟล์แนบของรายการเหล่านี้ และแจ้งในสรุปผล export ว่า "N รายการไม่มี GUID จึงไม่ได้แนบไฟล์ให้อัตโนมัติ กรุณาตรวจสอบด้วยตนเอง"
- ถ้ารายการมี GUID แต่ไฟล์แนบต้นทางหาไม่เจอ/เสียหาย → ไม่ทำให้ export ทั้งหมดล้มเหลว ให้ log ไว้ในสรุปผลว่า "N รายการไม่พบไฟล์แนบต้นฉบับ" แล้ว export ต่อ

## 2. ฝั่ง Import — รวมไฟล์แนบเข้าฐานข้อมูลหลักอย่างปลอดภัย

### 2.1 Preview Grid เพิ่มคอลัมน์
เพิ่มคอลัมน์ `จำนวนไฟล์แนบที่พบ` ใน `dgvImportPreview` เพื่อให้ผู้ใช้เห็นก่อน merge ว่าไฟล์นี้มีไฟล์แนบมาด้วยกี่รายการ

### 2.2 หลักการ Atomicity ระหว่างข้อมูล DB กับไฟล์รูป (สำคัญที่สุดของส่วนนี้)

OLEDB Transaction ป้องกันได้แค่ความถูกต้องของข้อมูลใน DB เท่านั้น **ไม่ครอบคลุมการ copy ไฟล์** ดังนั้นต้องออกแบบแยกให้ปลอดภัย:

1. ก่อน commit transaction ลง DB ให้ copy ไฟล์แนบทั้งหมดไปไว้ใน **โฟลเดอร์ staging ชั่วคราว** ก่อน (ยังไม่ใช่ตำแหน่งจริง)
2. ถ้า copy ไฟล์ staging สำเร็จครบทุกไฟล์ → ค่อย commit transaction ลง DB
3. ถ้า DB commit สำเร็จ → ค่อยย้ายไฟล์จาก staging ไปยังตำแหน่งเก็บไฟล์แนบจริงของระบบ (ตำแหน่งเดียวกับที่ `ExcelTransactionImport.vb`/ระบบเดิมใช้อยู่)
4. ถ้าขั้นตอนไหนล้มเหลว (copy ไฟล์ไม่ครบ, หรือ DB commit ล้มเหลว) → rollback DB ตามปกติ **และลบไฟล์ที่ copy ไปไว้ที่ staging ทิ้งทั้งหมด** ไม่ปล่อยให้ไฟล์ค้างอยู่โดยไม่มีรายการอ้างอิง

ลำดับนี้ป้องกันทั้งสองกรณี: DB มีรายการแต่ไม่มีไฟล์ และมีไฟล์ลอยอยู่โดยไม่มีรายการอ้างอิง

### 2.3 กันไฟล์แนบซ้ำเวลา import ไฟล์เดิมซ้ำ
- ถ้ารายการนั้นถูกตรวจพบว่าเป็น duplicate (ตามสเปค dedup เดิม) และถูกข้าม → ไม่ต้อง copy ไฟล์แนบของรายการนั้นเข้าไปซ้ำ
- ถ้าต้องการเช็คไฟล์แนบซ้ำแบบเนื้อไฟล์จริง (ไม่ใช่แค่ชื่อ) สามารถใช้ file hash เทียบก่อน copy ได้ แต่ไม่บังคับ — เป็นการป้องกันเสริม ไม่ใช่ requirement หลัก (เพื่อไม่ให้ระบบซับซ้อนเกินจำเป็น)

## ข้อควรระวังเพิ่มเติม

1. **ขนาดไฟล์รวมบน Flash Drive** — ถ้าจำนวนรายการเยอะและมีรูปแนบทุกรายการ ไฟล์รวมอาจมีขนาดใหญ่กว่าตัวข้อมูลตัวเลขมาก ให้ AI agent แสดงขนาดไฟล์รวมโดยประมาณก่อน export เริ่มทำงานจริง เผื่อ Flash Drive มีพื้นที่ไม่พอ (ไม่ต้องทำระบบบีบอัดไฟล์อัตโนมัติ เพราะเพิ่มความซับซ้อนเกินจำเป็นสำหรับตอนนี้ ถ้าพื้นที่ไม่พอให้แจ้งเตือนผู้ใช้พอ)
2. **ไม่ต้องแก้รูปแบบการเก็บไฟล์แนบเดิมของระบบ** — export/import ต้อง copy ไฟล์เข้า-ออกในรูปแบบเดียวกับที่ระบบเดิมใช้อยู่แล้ว (ตามที่ตรวจสอบได้ในข้อ 0) เพื่อไม่ให้ `ExcelTransactionImport.vb` หรือฟอร์มดูรายการเดิม เปิดดูรูปแนบของรายการที่ import เข้ามาใหม่ไม่ได้
3. **รายการเก่าที่ไม่มี GUID** — ยืนยันอีกครั้งว่าจะไม่พยายามจับคู่ไฟล์แนบอัตโนมัติให้กลุ่มนี้ เพราะเสี่ยงจับคู่ผิดไฟล์ ให้เป็นงานที่ผู้ดูแลตรวจสอบเองเป็นกรณีไป

## Deliverables เพิ่มเติมจาก AI Agent

1. รายงานกลับก่อนเริ่มแก้โค้ด ว่าปัจจุบันระบบเก็บไฟล์แนบแบบ path-reference หรือ OLE/BLOB (ตามข้อ 0)
2. ขยาย `FrmExportForTransfer.vb` ให้ copy ไฟล์แนบไปโฟลเดอร์ `Receipts/` ควบคู่กับไฟล์ข้อมูล ตั้งชื่อด้วย GUID
3. ขยาย `FrmMultiMachineImport.vb` ให้:
   - แสดงคอลัมน์จำนวนไฟล์แนบใน preview
   - ทำ staging-then-commit-then-move ตามข้อ 2.2 เพื่อความปลอดภัยของไฟล์คู่กับ DB transaction
   - อัปเดต `ImportHistory` ให้เก็บจำนวนไฟล์แนบที่ import สำเร็จด้วย
4. ทดสอบ round-trip พร้อมไฟล์แนบจริงอย่างน้อย 1 รอบ แล้วยืนยันว่าเปิดดูรูปจากรายการที่ import เข้ามาใหม่ได้ถูกต้องจากหน้าจอระบบเดิม (ไม่ใช่แค่เช็คว่าไฟล์ถูก copy ไปเฉยๆ)
